# FitConnect AI Constitution

**Status:** ENFORCED  
**Scope:** Entire FitConnect repository, database, Edge Functions, CI/CD, hosting, integrations and AI-assisted development  
**Priority:** Constitutional / highest project-level engineering authority

## 1. Prime Directive — Security First

Security takes precedence over speed, convenience, feature delivery and cosmetic CI success.

No change may knowingly weaken authentication, authorization, tenant isolation, RLS, secret handling, payment integrity, auditability or production traceability.

A warning may never be suppressed merely to make a dashboard green. The root cause must be understood, repaired, or explicitly documented as an accepted limitation.

## 2. Truthful Execution

AI agents and developers MUST distinguish between:

- inspected;
- implemented;
- deployed;
- tested;
- production-verified;
- certified.

A successful CI run is not proof of a successful production deployment.

Never claim a component is green unless evidence supports that exact state.

Never invent runtime state, credentials, DNS state, deployment state, database state, test results or security guarantees.

## 3. Safe Autonomous Operation

AI agents SHOULD work autonomously when the next action is evidence-based, reversible and within granted authority.

The required cycle is:

`READ -> AUDIT -> CLASSIFY -> REPAIR -> TEST -> VERIFY -> GREEN`

When a safe next action is proven, continue without unnecessary human interruption.

STOP and request human action only when required for credentials, billing/KYC, external account authorization, unavailable permissions, destructive ambiguity or another genuinely human-only boundary.

Never bypass a failed security control to continue faster.

## 4. Least Privilege

Default posture is deny-by-default and explicit allow.

- `anon` receives only intentionally public capabilities.
- `authenticated` receives only capabilities required by the signed-in user's role and tenant.
- `service_role` is server-side only.
- `SECURITY DEFINER` functions require explicit justification and authorization review.
- Internal trigger/scheduler functions MUST NOT be exposed as public RPC endpoints unless explicitly required.
- Administrative mutations MUST enforce administrative authorization server-side.

## 5. Multi-Tenant Isolation

Tenant isolation is mandatory.

Every tenant-scoped read or mutation MUST resolve and enforce the correct organization boundary server-side.

A user MUST NOT gain access to another organization's data by supplying another organization ID, record ID, cart ID, invoice ID, order ID or module ID.

Legacy membership fallbacks MUST NOT silently broaden access.

Fail closed when tenant membership or organization ownership cannot be proven.

## 6. RLS Constitution

RLS is a security boundary, not a convenience feature.

- Client-accessible tenant data MUST have explicit, tested policies.
- Server-only tables SHOULD remain inaccessible to `anon` and ordinary `authenticated` users.
- Public storefront policies MUST expose only intentionally public records.
- Admin logic MUST NOT be required by anonymous policies when a role-specific policy can be used instead.
- Policy changes require negative tests as unauthorized roles and positive tests as authorized roles.

## 7. Secrets Constitution

Secrets MUST NOT exist in browser bundles, static assets, repository source, migrations, logs, comments or user-visible responses.

This includes, without limitation:

- Supabase service-role credentials;
- Mollie private API keys;
- payment signing secrets;
- KVK private/test keys;
- mail-provider secrets;
- OpenAI API keys;
- third-party private credentials.

Secrets belong in approved secret/environment stores.

If exposure cannot be excluded, rotate the credential.

Public/publishable keys MUST still be protected by correct RLS and authorization boundaries.

## 8. Payment Constitution

Payment integrity is P0.

Until explicitly production-certified, Mollie MUST remain in TEST mode.

Payment flows MUST use server-authoritative:

- product identity;
- price;
- tax;
- currency;
- availability;
- inventory;
- organization ownership.

Production payment hardening MUST include rate limiting, one-time checkout nonces, signed short-lived status tokens, replay protection, webhook verification and idempotent processing.

Client-supplied prices or payment status MUST never be trusted.

Mollie LIVE activation occurs only after TEST end-to-end certification and security gates are green.

## 9. Authentication Constitution

Use the strongest controls available on the active Supabase plan without breaking legitimate flows.

Required where available:

- secure email change;
- secure password change;
- current-password verification for password updates;
- strong password requirements;
- leaked-password protection when supported by the subscribed plan.

Plan-restricted controls MUST be documented as `ACCEPTED / PLAN-LIMITED`, not falsely marked as repaired or ignored.

### 9.1 Command Center Authentication Ownership

**LAW_ADMIN_AUTH_SINGLE_OWNER**

The FitConnect Command Center MUST have exactly one canonical authentication/authorization owner.

- The central admin auth flow owns session validation, role authorization and auth-related redirects.
- `admin.js`, feature modules, renderers, stores and other secondary runtimes MUST consume the resulting authorization state and MUST NOT implement competing session/role redirect guards.
- Legacy admin login redirect chains MUST NOT be allowed to create login/admin ping-pong behavior.
- A technical authorization/bootstrap failure MUST fail closed without creating an uncontrolled redirect or request loop.

### 9.2 Authorization Bootstrap Determinism

**LAW_AUTH_BOOTSTRAP_DETERMINISM**

Every dependency required to make an authorization decision MUST be deterministically available before authorization executes.

Parser-injected, dynamically written, lazy-loaded or asynchronously initialized dependencies MUST NOT create a timing-dependent authorization boundary.

A compatibility bootstrap may be used only when it:

- is minimal and read-only where possible;
- preserves the same authorization semantics;
- does not weaken RLS, roles or permissions;
- is replaced by the canonical owner when normal initialization completes.

The production incident and recovery reference for these laws is maintained in:

`docs/ai-library/incidents/2026-08-13-command-center-auth-bootstrap-loop.md`

## 10. Edge Function Constitution

Every Edge Function MUST be classified as one of:

- public intentional endpoint;
- authenticated user endpoint;
- admin endpoint;
- webhook endpoint;
- internal/service endpoint.

For each function, review:

- authentication;
- authorization;
- tenant scope;
- input validation;
- CORS;
- rate limiting;
- secret handling;
- error disclosure;
- replay/idempotency requirements.

`verify_jwt=false` is permitted only when the endpoint intentionally implements an appropriate alternative security boundary.

Wildcard CORS MUST NOT be used for privileged endpoints without explicit justification.

## 11. FDMP and Ownership

FitConnect's FDMP v2 ownership model remains mandatory.

Domain ownership, repository ownership, state ownership and DOM ownership MUST NOT be bypassed by convenience patches.

Prefer the established flow:

`Renderer -> Store -> Service -> Repository -> Backend`

Cross-domain communication SHOULD use explicit events/contracts rather than hidden shared-state coupling.

Legacy direct database access MUST NOT be reintroduced where a repository boundary exists.

## 12. Database Change Law

Database changes MUST be migration-driven, minimal and auditable.

Before a destructive or privilege-changing migration:

1. inspect dependencies;
2. classify intended callers;
3. preserve legitimate flows;
4. apply the smallest safe change;
5. perform role-level regression tests;
6. rerun relevant advisors/tests.

Never alter privileges merely to eliminate an advisor warning.

## 13. Git and Release Governance

Production changes MUST be traceable to Git.

- Work on controlled branches.
- Use reviewable commits/PRs for material changes.
- CI guards remain mandatory.
- Temporary diagnostics MUST be removed before certification.
- `main`, deployment branches and production runtime MUST have an explicit release relationship.
- A production freeze requires an identifiable release SHA and verified deployment state.

### 13.1 Production Deployment Provenance

Production deployment configuration MUST identify the intended production branch explicitly.

A development, agent or hotfix branch MUST NOT become the Hostinger production source by accident.

Before diagnosing a production regression after a code repair, verify that the intended production SHA/branch is actually deployed. Deployment drift MUST be treated as a release-governance failure, not as proof that the code repair failed.

## 14. DNS, Web and Perimeter Security

Production certification includes the external perimeter, not only application code.

Audit where applicable:

- TLS/HTTPS;
- HSTS;
- Content-Security-Policy;
- MIME sniffing protection;
- clickjacking/frame protection;
- Referrer-Policy;
- Permissions-Policy;
- CORS;
- DNSSEC;
- CAA;
- SPF;
- DKIM;
- DMARC.

Unverified controls MUST remain unverified rather than being assumed green.

## 15. No Security Theatre

Do not optimize for a green dashboard at the expense of real security.

A control is green only when its intended security property has been demonstrated.

Accepted exceptions require a reason, scope and owner/constraint.

## 16. Regression Law

Every security hardening change MUST be tested for legitimate-function regression.

At minimum, where relevant, test as:

- anonymous/public user;
- ordinary authenticated customer;
- tenant member;
- administrator;
- service/backend role.

A fix that blocks legitimate public storefront behavior is not complete.

### 16.1 Admin Authentication Regression Gate

Any modification to Command Center authentication, Supabase client bootstrap, CustomerRepository authorization, admin routing or admin script load order MUST include regression checks for:

- anonymous `/admin/` access;
- authenticated non-admin `/admin/` denial without redirect loops;
- authenticated admin `/admin/` stable authorization;
- authenticated customer portal stability;
- admin refresh stability;
- deterministic logout;
- absence of repeated profile/theme/bootstrap request storms.

HTTP 429 caused by a client navigation loop MUST be classified as downstream damage. The earliest failing auth/bootstrap boundary must be repaired rather than weakening rate limits.

## 17. Human Escalation Law

Human intervention is reserved for actions the automation cannot safely or legitimately perform, including examples such as:

- entering or rotating private secrets in an external dashboard;
- Mollie KYC/live activation;
- billing/plan upgrades;
- Hostinger/DNS account actions unavailable to tooling;
- irreversible decisions requiring business authorization.

Never ask the human to perform work that available project tooling can safely perform autonomously.

## 18. Production Certification Gates

No Enterprise Production Freeze may be declared until the applicable gates are green:

1. Database privilege security
2. Authentication and secrets
3. Payment security
4. Mollie TEST end-to-end certification
5. Runtime/legacy cleanup
6. Database performance baseline
7. Internet perimeter security
8. Backup/recovery and cross-browser production certification

Only after these gates may Mollie LIVE activation and final production certification proceed.

## 19. Current Accepted Plan Limitation

Supabase controls that require a higher subscription tier may remain unavailable on the current plan.

They MUST be recorded as `ACCEPTED / PLAN-LIMITED` and reconsidered when the subscription changes.

A plan limitation does not authorize weakening controls that are available on the current plan.

## 20. Constitutional Enforcement

When an implementation request conflicts with this constitution, the safer constitutional rule wins unless the constitution itself is deliberately amended through an explicit governance change.

Security regressions are release blockers.

## 21. AI Incident & Solution Library

Production incidents with reusable engineering value MUST be documented under:

`docs/ai-library/incidents/`

Each incident record SHOULD contain:

- problem and observable symptoms;
- affected and unaffected surfaces;
- evidence and diagnostic fingerprints;
- root cause;
- contributing conditions;
- implemented solution and relevant PR/commit references;
- security properties preserved;
- regression tests;
- prevention laws;
- recovery playbook.

The purpose of this library is to prevent future AI agents and developers from rediscovering solved production failures through trial and error.

**FitConnect principle:** Build fast only where we can prove we remain safe.
